# 门：阶段一与阶段二之间的硬闸

## 为什么必须是硬闸

正文一旦写起来，一个错数会同时污染表格、正文点评、Summary 的回指和跨节交叉引用。改一个数的代价从「重跑 2 分钟脚本」变成「重写半个章节」。所以图和数必须先由人签过，才允许动正文。

## 门开在哪

```
阶段一：认文件 → 抽数入账本 → 自查 → 出图 → 生成核对清单
                                                    ↓
                                            【门】人工校对 + 签收
                                                    ↓
阶段二：校验签收 → 逐块写正文 → 插图出 docx → crosscheck → 交付
```

## 阶段一收尾要交出的两样东西

1. **`out/` 里的 22 张 PNG**（21 图 + T1）
2. **`out/REVIEW_<CQ>.md` 核对清单** —— `review_sheet.py` 生成，两部分：
   - **算术恒等式自查结果**（不占用户时间）：资产类别 debt+equity=100%、senior secured = 一留+二留、行业占比前 10+Other=100%、评级四档=100%、非应计成本口径 ≥ 公允值、覆盖率 = NII÷总分红。**恒等式不通过不许进门**，先修数。
   - **本季新增每个数一行**：图/表、系列、上季、本季、QoQ、出处。用户逐行核。

把这两样发给用户，明确说「请逐张看图、逐行核数，确认后我再写正文」。**然后停下等。**

## 签收机制

用户确认后跑：

```bash
python3 approve.py --sign      # 落 APPROVED_<CQ>.json
```

签收文件记 `CQ`、`series.json` 的 sha256、每张 PNG 的 sha256。

阶段二启动前必须跑：

```bash
python3 approve.py --check     # exit 0 才许继续
```

**任何一张图被重出、或账本被改过，校验就失败** —— 改动过的部分要重新交给用户校对再签。

## 三条铁律

**一、没有有效签收，阶段二拒绝启动。** 不许用默认值、不许「先写着等下再核」。**定时任务或无人值守场景下也必须停在门口**，把清单留在 `out/` 里等人回来。

**二、门可以跨会话。** 用户校对可能隔几小时甚至隔天，那时会话早断了。签收文件落在磁盘上，所以阶段二可以是**全新一次会话** —— 读账本 + `out/` + 签收文件即可开工。这也顺带解决上下文问题：生图和写正文本来就不该挤在一个会话里。

**三、用户在门口提出的修改，改完要重新签。** 比如「图 12 的 y 轴太挤」「图 6 那个 0.6% 核对下」—— 改完重跑 `build_charts.py`，PNG 的 sha256 变了，旧签收自动失效，必须重新交付清单、重新签。这是设计意图，不是麻烦。

## 可选的第三道门

正文四块（Summary / 1.News / 2.OTF update / 3.BDC 行业 / 4.软件 AI）**建议每写完一块就交给用户看一次**，而不是四块写完一起看。理由：图的错是算术错、程序能兜；正文的错是判断错（thesis 立错、观点环比记错、key debate 抓错重点），只有人能看出来，而且一块写错会污染 Summary 和后面几块的回指。分块看的返工量比一次看小得多。

这道门不强制。用户嫌停太多次时可以合并成「2 大块看一次」，但**不要一路写到底再看**。
